# KICK emulator

Runs the real Kick app on macOS, Linux and Windows against a virtual control surface, before the hardware exists. Kick itself is unmodified apart from `KICK_EMU` guards that route hardware access to stand-ins.

Two parts:

- **Kick (`-DKICK_EMU=ON`)** is the normal app target built for the host OS. The modules the public release lacks (`AudIO_juce`, `AudIO_constants`, `juce_serialport`, `PktMgr`) are clean-room stand-ins in `emu/modules/`. The `kick_emu` module holds the app-side hardware layer and a control socket.
- **KICK Surface** (`emu/surface/`) is a separate JUCE app that plays the MCU: pads, buttons, Q-link knobs, encoder, touch strip, LEDs, CV meters, SD and USB slots. It looks like the unit's front panel and shows Kick's screen inside its bezel. It talks to Kick over a pty (macOS, Linux) or TCP (any OS, always on Windows) using the PktMgr serial protocol.

The app icon is generated by `emu/tools/make_icon.py` (Pillow, writes `emu/surface/icon/`).

Stage 2 (not built yet) is a QEMU aarch64 VM running the Buildroot rootfs with the same Surface attached over TCP (`--tcp`).

## Platforms

| Host | Build | Run | Tested on |
|---|---|---|---|
| macOS | `emu/build.sh` | `emu/run.sh` | macOS 26, Apple Silicon |
| Linux | `emu/docker/run-linux.sh build` (or `emu/build.sh` with the packages in `emu/docker/Dockerfile`) | `emu/docker/run-linux.sh test`, or `emu/run.sh` under a display | Ubuntu 24.04 arm64 in Docker, Xvfb |
| Windows | `emu\build.ps1` | `emu\run.ps1` | Windows 11 ARM64 VM, Visual Studio 2022 (MSVC 14.44), Release |

Windows x64 and Linux x86_64 use the same code but are untested. The Linux Docker build needs about 4 GB free for the heaviest translation unit, so it builds Release with one job (`JOBS=1`).

## Build and run

```bash
emu/build.sh            # Kick + Surface into build/emu and build/surface
emu/run.sh              # opens both windows
emu/run.sh --root DIR   # device root, default ~/KickEmu
emu/run.sh --script emu/tests/smoke.script   # headless run, exit code = result
```

Needs Xcode, cmake, ninja, python3. On Windows, `emu\build.ps1` uses the CMake and Ninja that ship with Visual Studio 2022 (C++ workload) and `emu\run.ps1` takes `-Script`, `-Root` and `-Port`; clone with `core.autocrlf=false` so the JUCE patch applies. Demo samples need Python 3 on Windows (`winget install Python.Python.3.12`), otherwise they are skipped. The first build fetches JUCE 7.0.12 and other deps through CPM and applies `emu/patches/juce_7.0.12_macos15_sdk.patch`.

`run.sh` generates 16 synthesized one-shots in `<root>/data/sounds/Emu Kit` on first run. Kick's demo projects are empty, so assign samples to pads from the Kick UI before expecting sound.

## Device root

Everything Kick expects at a Linux path lives under `KICK_EMU_ROOT`:

| Device path | Emulated as |
|---|---|
| `/dev/ttymxc0` | symlink to the Surface pty, or `KICK_SERIAL_PORT=tcp://127.0.0.1:50910` when the Surface serves TCP |
| `/mnt/sdcard`, `/mnt/flash` | `<root>/mnt/...`, shown when the SD/USB toggles are on |
| `/dev/mmcblk1`, `/dev/sda` | marker files the Surface creates for SD / USB presence |
| `/home/Kick/{projects,logs,prefs}` | `<root>/home/Kick/...` |
| `/data/sounds` | `<root>/data/sounds` (factory samples) |
| `/sys/devices/soc0/serial_number` | serial, default `KICKEMU0001` |
| I2C bus 3, addr 0x0C | virtual CV DAC, drives the Surface CV meters |
| backlight, `reboot`, `poweroff` | forwarded to the Surface as events |

## Surface

Mouse: click pads and buttons, drag knobs, drag or scroll the jog wheel (click it for Enter), drag the touch strip, and touch Kick's screen in the bezel. The dev drawer (the `dev` button) holds the velocity and pressure sliders, the SD and USB toggles, the CV meters and the packet log.

Dual-legend keys (BANK A / E, MAIN / GRID and so on) send the printed primary id, and the second legend while Shift is held. Clicking SHIFT latches it. This is an assumption about how the unit's MCU sends the shifted layer, so check it against hardware before relying on it. The unit has only four Q-Link knobs, P1 to P4, so they send knobs 1-4 and the drawer's page buttons move them to 5-8, 9-12 or 13-16. MASTER and REC are analog on the unit and only turn on screen.

Keyboard: pads `z x c v / a s d f / q w e r / 1 2 3 4` (bottom row first), space = Play, return = Enter, arrows = Knob CCW/CW, esc = Back, tab = Stop, shift = Shift, up/down = encoder.

Script commands (`--script`, `#` comments): `wait ms`, `pad 1-16 [vel] [holdMs]`, `button name|id [holdMs]`, `knob 0|1-16 steps` (negative = CCW), `slider 0-100` (the strip is vertical), `sd in|out`, `usb in|out`, `snapshot file.png`, `expect connected`, `expect pad n colourId|off`, `expect led name on|off`, `expect cv ch minVolts`, `quit [code]`.

## Control socket

Kick listens on `127.0.0.1:50901` (`KICK_EMU_CONTROL_PORT`), one command per line:

```
ping
snapshot <file.png>   (.png inside the device root or the system temp dir; relative paths resolve against the root)
tap <x> <y> [holdMs]
drag <x1> <y1> <x2> <y2> [holdMs]
down|move|up <x> <y>  (live pointer, used for the bezel; a leading ! suppresses the reply)
quit
```

The socket is localhost only. A first line that is not a known command closes the connection, which stops browser cross-protocol requests from reaching later lines.

Taps go straight to the component under the point. Injecting through the window peer fails on macOS unless the window is topmost.

Kick also streams its window to the Surface on TCP `50903` (`KICK_EMU_FRAME_PORT`, `KICK_EMU_FRAME_FPS` default 30) and minimises its own window; `KICK_EMU_SHOW_WINDOW=1` keeps it visible.

The Surface listens on UDP `50902` (`KICK_EMU_EVENT_PORT`) for `cv ch raw volts`, `backlight N`, `power reboot|off`, `app started|stopped`.

## Serial protocol

230400 8N1, frames `'M' 'T' type dir cmd size data[size-1] crc8`. CRC-8 poly 0x31, init 0xFF over every prior byte. `size` is data length + 1. Frames to the app carry one trailing `'\n'` because the app's reader takes `size+7` bytes. Frames from the app have no trailer. A frame with no data hangs the app parser, so the Surface never sends one.

Types: SYSTEM 0, BUTTON 1, LED 2, PAD 3, KNOBS 4, MIDI 5, CV 6, SLIDER 7. Handshake: app sends COMM_INIT[1], Surface answers SW_VER[1,0] and status[1], app sends COMM_INIT[2], Surface sends status[2], app answers status[2], link is live. The Surface heartbeats status[2] about every 3 s.

## Assumptions and limits

- The stand-in modules are written from how Kick calls them, not from the closed originals. `AudIO_constants` values are guesses sized to work.
- Audio uses the default CoreAudio output at 48 kHz, 256 frames.
- The camera is a placeholder on the panel. Kick has no camera code.
- Linux and Windows audio use the host's default device. The Docker run has none, so it only proves boot and the UI.
- Pad aftertouch is sent but the app ignores it.
- Pad LEDs only light when the app sets them (some modes need a loaded program).
- Wifi, firmware update, and resource-update paths are Linux-only and not emulated.
- Stage 2 (QEMU + Buildroot) is not started.
